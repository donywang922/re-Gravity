# re-Gravity 多体引力与碰撞模拟器：架构规范与设计草案

本系统旨在 VRChat 限制环境（无 Compute Shader，无多渲染目标 MRT）下，利用 GPU 片元着色器和 Custom Render Texture (CRT) 实现最高 65,536 个天体的实时 N-Body 引力模拟与物理碰撞。

## 1. 核心架构与调度机制

系统采用固定大小为 256 × 256 的双缓冲 CRT 矩阵存储天体状态。每个天体在其生命周期内拥有绝对固定的像素位置（UV 坐标）。
在 C# (UdonSharp) 侧（`GravitySimulator.cs`），系统通过显式的手动 Ping-Pong 状态机，规避 Unity 原生双缓冲在时间切片下更新不一致的问题。

更新分为三个阶段（Phases）：
*   **Phase 1 (`VelMiscUpdate`)**：按设定的批次分片执行（以避免掉帧），负责处理引力场积分、碰撞预判与状态机流转。
*   **Phase 2 (`PosMassUpdate`)**：在 Phase 1 的所有批次执行完毕后，统一执行一次，根据 Phase 1 下达的事件执行位置位移和最终质量结算。
*   **Phase 3 (`EventDataUpdate`)**：随 Phase 2 同步执行，根据前序事件计算并缓存用于下一帧的物理方向（如碎片飞溅方向）和受损质量。

## 2. 数据与显存编码结构

系统的数据严格打包在 `float4` 中：

*   **PosMass (运动学与质量)**
    *   `XYZ`: 天体绝对世界坐标。
    *   `W`: 天体质量。质量低于阈值视为死星或微小尘埃。
*   **VelMisc (动力学与事件总线)**
    *   `XYZ`: 速度向量。
    *   `W`: 事件信号总线 (EventSignal)。利用底层位操作/浮点编码机制（约等于 `数据*8 + 事件类型`）对目标 ID 与事件进行打包。
*   **EventData (碎片与特效计算缓冲)**
    *   `XYZ`: 碰撞法线或碎片喷射偏转向量。
    *   `W`: 质量损失量。
*   **TrailHistory (轨迹历史缓冲)**
    *   256 × 64 的 CRT。宽度代表 256 个历史坐标帧，高度代表被追踪的质量最大的 64 个天体，用于 GPU 纯程序化长尾轨迹渲染。
*   **Color (星空主题配色)**
    *   一次性生成颜色的静态缓冲。

## 3. 事件机制与状态机

天体交互事件按以下优先级进行判定（优先级由上至下递减）：

1.  **被吞噬 (EVENT_SWALLOWED - 2)**：当两核心（内层）相交，质量较小者直接判死并被完全吞噬，产生少量爆散碎片。
2.  **被吸收 (EVENT_ABSORBED - 3)**：外层相交且预测下一帧仍继续相交时，较小方开始被吸取质量。
3.  **质量结算 (EVENT_MASS_SETTLE - 1)**：大天体在吞噬/吸收对方时，在此状态下累加对方的质量与动量。
4.  **破碎 (EVENT_SHATTER - 4)**：外层相交但预测下一帧分离，属于非弹性擦碰，带出表面碎片并损失少量动量。
5.  **撕裂 (EVENT_TEAR - 5)**：未直接接触但距离小于洛希极限时，天体开始向引力源缓慢抛射自身质量。
6.  **死亡 (EVENT_DEAD - 6)**：生命周期结束的天体。
7.  **重生 (EVENT_RESPAWN - 7)**：死亡的天体会根据全宇宙的碎片生成概率，在发生碰撞/撕裂的位置重新随机复活为质量极小的碎片，并继承相应的抛射速度。
8.  **无事件 (EVENT_NONE - 0)**：天体平稳运行中。

## 4. 全局物理与控制机制

*   **内外层双密度模型**：天体物理体积由内部核心（如花岗岩密度）和外部壳层（如水密度）组成。碰撞判定依据内层与外层的触碰深度决定是合并、摩擦还是撕裂。
*   **分批次算力调配**：`GravitySimulator.cs` 实时监控游戏帧率（平均 Delta Time）。当帧率跌破 50 fps 时，系统自动下调单帧处理天体数量（增加分批数，至多 256 批），使用 GPU Warp 早期退出（Early-Exit）机制跳过不属于当前批次的计算。
*   **惰性动量修正与重居中**：物理系统在极长时间运行后可能产生坐标漂移。当需要重置原点时，系统利用 `VRCAsyncGPUReadback` 将天体坐标和速度全部拉回 CPU 进行质心与系统总动量计算，并在下一个 Shader 更新周期施加一个统一的负补偿（Offset），将整个星系稳固地拉回玩家视野中心。

## 5. 用户界面 (UI) 与交互规划

*   **调出方式**：PC 玩家按下 `Tab` 键呼出；VR 玩家可通过**双击扳机键 (Trigger)** 或**按住握把键 (Grip) 并向右滑动**来展开主控面板（向左滑动关闭）。面板具有初始延迟（方便同步玩家身高），并在距离玩家过远（> 3米）时自动闭合。
*   **UI 层级结构**：
    *   **启动页**：全局物理参数（最大天体数、步长、倍率、分批次数），包含开始/暂停、重新居中、保存快照等系统级操作。
    *   **设置页**：细化控制。包含特效亮度（闪光、自发光、模型灯光）和物理常数（引力常数、销毁半径、生成半径、初始化大小等）。
    *   **玩家页**：显示当前世界内的玩家列表。若其他玩家抓取了快照，这里会显示相应的“同步”按钮供你下载该玩家的快照。
    *   **画笔页**：快捷调用三维画笔 (QvPen) 进行空间标注。
    *   **调试与介绍页**：包含底层参数监视器（物理步长、目标CRT、批次等），以及完整的原理简介文档。

## 6. 网络同步（快照系统）

系统通过一套高度定制化的分块传输协议在 VRChat Udon 网络中共享多体系统的宏观状态：
*   **本地快照抓取**：当玩家发起快照请求时，引擎通过 `VRCAsyncGPUReadback` 异步读取当前 65,536 个天体的坐标与速度，并在本地过滤掉所有死亡（`EVENT_DEAD`）或无质量的天体，将有效天体缓存在本地数组中。
*   **分块传输协议 (Chunk-Based Sync)**：
    *   **请求队列**：接收方通过其 `PlayerState` 的同步变量（Udon Sync）向拥有快照的发送方发起请求。发送方维护一个请求队列，依次处理不同玩家的下载请求。
    *   **数据分片**：发送方通过 `TransferChannel` 将上万个天体数据切分为每个大小为 128 (CHUNK_SIZE) 的数据块进行网络分发。
    *   **握手与确认 (ACK)**：接收方收到每个 Chunk 后，通过更新 `PlayerState.ackChunk` 来通知发送方继续发送下一个数据块。内置了超时检测与重传机制（Retry），保障海量数据的可靠到达。
*   **反序列化与复原**：接收端下载完所有有效天体数据后，将数组中未使用的空闲槽位填充为死亡信号（而非随机碎片），最后通过 C# 将整块数据重写给 CRT（`Blit`），保证了多体宇宙的同步稳定并大幅压缩带宽占用。
