# VRChat 65,536 多体引力与碰撞模拟器：工程架构草案

## 核心架构与调度机制

本系统旨在 VRChat 限制环境（无 Compute Shader，无多渲染目标 MRT）下，利用 GPU 片元着色器实现 65,536 个天体的实时 N-Body 引力模拟与物理碰撞。

系统采用固定大小为 256 \* 256 的 Custom Render Texture (CRT) 矩阵存储天体状态。每个天体在其生命周期内拥有绝对固定的像素位置（UV 坐标）。 通过在 UdonSharp 中实例化两组 CRT（A组与B组），系统建立显式的手动 Ping-Pong 状态机，以规避 Unity 原生双缓冲在时间切片下的数据撕裂问题。

## 数据与显存编码结构

### 常量：只能在编辑器里修改的数值

* 内层密度：默认同花岗岩  
* 外层密度：默认同水  
* 内外比例：内外层占天体半径的比例，默认50%  
* 最小可见质量：小于这个质量的天体将不被渲染  
* 最小发光质量  
* 尘埃采样次数：每个尘埃将随机采样多少次EventData  
* 碎片大小范围：同时决定平均碎片大小  
* 尘埃生成半径  
* 销毁半径

### 变量：用户可以在UI中修改的数值

* 最大天体数量：pc默认32768，quest默认8192  
* 最大步长：默认0.05（1/20秒）  
* 模拟速度：默认1，物理的倍率  
* 分批次数：0-256，默认0（自动），用于将VelMisc的更新按行拆分为多次，至多256次，即每帧更新一行256个天体。  
* HSL：三个范围，用于随机生成Color贴图  
* 闪光亮度：0-8，默认2  
* 天体亮度：0-1，默认1  
* 轨迹数量：0-64，默认16

### CRT：Float32 RGBA格式，存储天体的全部数据。

* PosMass (运动学)  
  * XYZ: 天体绝对世界坐标。  
  * W: 天体质量。质量低于阈值视为不可见尘埃。  
  * 需考虑物理步长  
  * 全量更新  
* VelMisc (动力学与事件总线)  
  * XYZ: 速度向量。  
  * W: 事件信号总线 (EventSignal)。通过 Float32 编码目标 ID 与事件类型（EventType\*10000+targetID）。  
  * EventType，1：吞噬，2：被吞噬，3：碰撞破碎，4：撕裂  
  * 由于O(n^2)计算量，可能会分批更新  
* Rotation (自转学)  
  * XYZ: 自转轴与角速度。  
  * W: 预留扩展参数。  
  * 需考虑物理步长  
  * 全量更新  
* EventData (碎片与特效)  
  * XYZ: 碰撞法线或碎片喷射偏转向量。  
  * W: 碰撞引发的质量损失与闪光特效计时器。  
  * 闪光计时器数值 \* 100,000.0  \+ 质量损失量   
  * 闪光计时器为0到300。  
  * 质量损失量负值为撕裂质量，正值为碰撞质量。  
  * 质量损失不可以超过最大天体数量\*10  
  * 质量损失只会存在一帧。  
  * 闪光计时器不考虑物理步长，每帧减一，约产生三秒闪光。  
  * 全量更新  
* Color (星空主题配色)  
  * XYZ: rgb数据  
  * 该贴图仅在用户点击启动模拟或更换主题时刷新一次。它接收用户设定的色板参数与随机种子，一次性为 65,536 个固定 UV 槽位生成对应的宇宙主题颜色。物理与碎片系统复活天体时直接复用该槽位的既定颜色。  
* Stats (全局聚合统计)  
  * 16 \* 8 的 CRT。使用 64 个并发线程分别遍历 1024 个天体，将总质量、总动量和质心质量矩累加为颜色输出。   
  * 左半区 (X坐标 0\~7)：物理量汇算，输出格式：float4(动量X, 动量Y, 动量Z, 总质量)  
  * 右半区 (X坐标 8\~15)：几何量与对象池汇算，输出格式：float4(质量矩X, 质量矩Y, 质量矩Z, 尘埃数量)  
  * Udon 回读后，遍历前 64 个像素，将其 R、G、B 累加为总动量，A 累加为绝对总质量；遍历后 64 个像素，将其 R、G、B 累加为总质量矩（用于算质心），A 累加为精确的尘埃总数。  
* TrailHistory (轨迹历史缓冲)  
  * 尺寸为 256 \* 64 的 CRT。宽度代表 256 个历史坐标帧，高度代表被追踪的 64 个最大天体。专门用于纯 GPU 驱动的轨迹渲染，避免大量 CPU 寻址开销。 

## 设计与机制

天体：基本单位，每个天体在逻辑上被划分为内层（核心）与外层（地壳/大气），两者的物理属性与交互逻辑完全独立：  
内层（核心）：默认密度等同于花岗岩。代表天体的刚性主体，其半径用于判定是否发生绝对的实体吞噬。  
外层（地幔/大气）：默认密度等同于水。外层包裹在内层之外（内外层半径比例默认设为 50%，可在初始化时调整），用于判定是否发生表面摩擦与碎裂。

天体同时带有自转数据，自转角度和速度随破碎和吞噬发生时两个天体的数据更新更新。自转数据用于配合天体运动数据决定碎片产生的方向和速度。

斥力：可见天体附近存在微弱的、略大于引力且极速衰减的斥力，以此阻碍微型可见天体轻易合并，促进星环的形成。当四个质量为10的天体处于一条线上时，引力应大于斥力。

洛希极限撕裂 (Tearing)：当两个天体并未直接相交，但极度靠近跨越洛希极限时。系统在 EventData 中记录撕裂方向并累加质量损失。天体开始缓慢剥离自身质量，并沿着朝向引力源的向量方向抛出极小的碎片天体。

外层碎裂 (Shattering)：当两个天体的外层发生物理相交，但内层核心仍未触碰。判定为非弹性擦碰。双方天体不发生合并，但会根据相交的区域大小和自转数据损失质量和自身动量，同时更新自身自转数据，并在碰撞切面法线方向产生大量碎片。若天体在此前已经处于撕裂状态，撕裂带来的质量损失会立刻一次性结算为碎裂损失。碰撞切面法线需考虑天体自转。

计算质量损失时需要考虑物理步长。

内层吞噬 (Swallowing)：当两个天体的内层核心相交。触发合并事件。较小天体瞬间宣告死亡（转化为尘埃），较大天体吸收对方的剩余质量与动量。如果在相撞瞬间双方仍携带有未结算的质量损失记录，这些损失会全额转化为爆散的碎片能量。吞噬将使天体闪光。

即便两个天体立即内层相交，也先计算破碎，保证无论如何都会都能产生质量损失和碎片。

EventData：记录事件产生的质量损失和碎片生成时的方向。

尘埃：所有小于最小可见质量的天体。  
当任意天体被吞噬后，在宇宙边缘复活为随机质量尘埃。

碎片：尘埃会随机采样EventData，如采样到任意质量损失，则根据当前尘埃总数，损失的质量，尘埃采样次数，按概率转化为碎片。总体每（平均碎片大小）质量损失将产生一个碎片。生成位置和动量由EventData中的类型和角度决定。碎片生成时将闪光。碎片质量在碎片大小中随机。

模拟开始时，所有天体都是碎片。碎片质量在碎片大小中随机。

尘埃和初始碎片将带有初始动量，动量总是大致上绕质心沿竖轴顺时针方向。动量大小随机。

## 数据更新

VelMisc：按分批次数拆分为多次，Udon 每帧将当前批次的 StartID 和 EndID 传递给 Shader 的全局变量。Shader 利用 GPU 线程束（Warp）的早期退出特性，在代码首行拦截不在当前区间的像素。非目标区间的线程直接返回旧缓冲数据，从而在硬件底层实现高效的算力剔除。 利用硬件级 rsqrt (平方根倒数) 指令，将引力与斥力的距离衰减公式改写为无除法、无开方的全乘法流水线，大幅削减 ALU 周期消耗。 在循环体内，同步进行引力累加与碰撞距离判定。若距离达到碰撞/撕裂阈值，向 VelMisc.w 写入事件信号。

EventData：在VelMisc更新完成后的下一帧全量更新。根据VelMisc中的碰撞数据更新损失质量和方向。如果没有发生碰撞，需将质量损失归零。

PosMass，Rotation，Stats，TrailHistory ：在EventData更新后立即全量更新。

为解决多并发碰撞导致的质量复制或死锁问题，实施严格的双向确认机制：

* 猎物在被多个捕食者包围时，其事件信号仅记录质量最大的捕食者 ID。  
* 捕食者在吞并目标增加自身质量前，必须跨纹理读取目标的事件信号，确认猎物的信号确实指向自己。握手成功后，才执行质量合并与动量守恒结算。未成功握手的碰撞将被顺延至下一个物理 Tick 处理。

## 物理

物理步长：两次PosMass更新的时间间隔，物理步长不会超过最大物理步长。注意由于VelMisc可能被拆为多个批次，两次PosMass更新间隔可能超过一帧。

分批次数：自动模式下默认为1，Udon 实时监控 Time.deltaTime。若连续多帧低于 90 FPS，Udon 将自动下调单帧处理的天体数量（即增加分批次数）。该数值仅可向分批更多、每帧计算更少的方向调整，彻底根除性能波动导致的瞬间卡顿。如果玩家手动调过分批数量，则不会再触发自动调整。

模拟速度：物理步长的倍率，所有标注需考虑物理步长的部分均指 物理步长\*模拟速度 。

## 宇宙环境约束与坐标基准

被动越界销毁：当检测到天体距离原点超过销毁半径且速度向量朝向宇宙外部时，判定为逃逸。直接按被吞噬处理（作为尘埃复活）。

渲染层主动视觉锚定：Udon 通过 Tex\_Stats 获取系统精确的质心坐标。所有天体渲染和轨迹绘制在 Vertex Shader 中应用统一偏移：P\_visual \= P\_physics \- Center。保证整个星系在玩家视野中永远稳固悬浮于中心。

惰性动量修正：当质心坐标在物理空间的绝对漂移超过 10000 单位时，Udon 挂起一次修正中断。在当前全宇宙物理 Tick 彻底结束的空隙帧，插入一次全屏 Shader 更新，将所有天体坐标减去质心，速度减去系统平均速度。此操作一次性抹平高位浮点精度误差，并同步重置轨迹追踪器的历史点阵。

## 表现层与渲染技术

### 1\. 球体伪装者 (Sphere Impostors)

天体渲染放弃传统的 3D 网格，使用包含了 65,536 个独立 Quad 的单次 DrawCall 网格。 在 Fragment Shader 中，利用数学公式计算虚拟球面的 3D 凸出高度，并强制覆盖深度缓冲 (SV\_Depth)。实现完美的体积前后遮挡和天体相交时的弧面穿插。颜色表现直接通过当前顶点的固定 UV 坐标去采样静态的 Tex\_Color 主题贴图，实现物理计算与美术管线的彻底解耦。天体会随与玩家的距离逐渐降低颜色亮度和饱和度，最低不会低于原数值的一半。

### 2\. 局部时间戳插值

由于分批机制，天体位置的更新速度至多为2帧一次，随分批数量而降低。顶点着色器读取此时间戳，使用公式 P \= P\_{old} \+ V \\cdot \\Delta T 进行独立插值，使帧率较低的底层物理能够映射为头显中 90Hz 的平滑运动轨迹。

### 3\. 顶级天体追踪与动态轨迹 (Top 64 Trajectories)

为避免 64 个原生的 Unity TrailRenderer 造成巨大的 CPU 性能损耗，轨迹追踪采用“Udon 异步回读筛选 \+ GPU 纯程序化渲染”的混合架构：

* 数据回读与最小堆筛选：Udon 设定一个低频计时器（例如每 1 秒触发一次），利用 VRCAsyncGPUReadback 将 PosMass 的 1MB 数据异步拉回 CPU。在 UdonSharp 中使用时间切片，维护一个容量为 64 的最小堆（Min-Heap），分 4 到 5 帧遍历 65,536 个天体质量，筛选出当前宇宙中质量最大的 64 个天体 ID。  
* ID 下发与历史录制：筛选完成后，Udon 将这 64 个 ID 写入一个全局缓冲区。TrailHistory (轨迹历史 CRT) 根据这 64 个 ID 实时去 PosMass 中采样它们的最新物理坐标，减去质心偏移后，以类似游标卡尺的机制向右滚动写入历史列中。  
* 单 DrawCall 轨迹绘制：编写一个自定义的 Line Renderer Shader，一次性生成 64 \* 256 个顶点的面片。该 Shader 直接读取 TrailHistory 中的坐标矩阵进行连线，并在渲染时根据首尾索引计算渐变透明度。从而以几乎为 0 的 CPU 开销，完美呈现最多 64 条长尾动态轨迹。

### 4\. 闪光与发光

闪光：在20帧内达到最高亮度，保持50帧，然后逐渐减弱。  
发光：超过最小发光质量的天体将自发光，随质量增加，最大不超过 闪光亮度/2。  
天体亮度：闪光亮度和颜色亮度乘以这个值。

### 快照打包与同步

利用 UdonSharp 对 CRT 数据进行序列化，用于玩家间快照分享。 序列化算法具备自动过滤机制，扫描到质量低于显示阈值的天体（尘埃）或空闲槽位时，直接跳过其位置与速度数据的打包。接收端反序列化时，用随机生成的尘埃数据填充剩余槽位。此机制大幅度压缩了网络带宽占用，保障 VRChat 房间的数据通讯稳定性。

## 踩坑记录

1\. \*\*VRChat Udon 与 Unity API 限制的踩坑\*\*  
 \* \*\*全局 Shader 变量赋值失效\*\*：最初试图使用 Unity 原生的 Shader.SetGlobalTexture 来广播双缓冲贴图。但在 VRChat 中该 API 被完全封禁。修正为使用 VRCShader.SetGlobalTexture，并且强制要求所有暴露给全局的 Shader 变量名称必须以 \_Udon 作为前缀。  
 \* \*\*局部更新 API 缺失\*\*：最初计划使用 CustomRenderTextureUpdateZone 来实现分批渲染以均摊算力。但该结构体未向 Udon 暴露。修正为利用 GPU Warp 的 Early-Exit（早期退出）特性，通过全局变量传递 StartID 和 EndID，在 Shader 首行进行 if 拦截，实现了等效的算力剔除。  
 \* \*\*CRT 初始化顶点着色器宏错误\*\*：最初为初始化材质编写了 \#pragma vertex CustomRenderTextureVertexShader。根据 Unity 文档，初始化阶段渲染的是全屏 Quad，必须使用专门的 InitCustomRenderTextureVertexShader，否则无法正确输出像素数据。  
  \* \*\*性能评估忽略 L2 缓存\*\*：最初单纯以显存带宽（GB/s）评估 O(N^2) 遍历的开销，得出需要顶级显卡的结论。实测与重新分析证实，65,536 个天体的数据量仅为 1MB，能够完美驻留在现代 GPU 的 L2 缓存中，触发缓存广播机制。真正的瓶颈仅为 ALU（算术逻辑单元）的纯浮点算力。  
 3\. \*\*渲染表现层的踩坑\*\*  
 \* \*\*单 Mesh 广告牌的深度相交失效（纸片人问题）\*\*：最初使用面片（Quad）渲染海量天体，导致天体靠近时出现扁平的深度穿插，且透明度遮挡失灵。修正为球体伪装者（Sphere Impostors），在片元着色器中计算 3D 凸起高度并手动覆盖深度缓冲（SV\_Depth）。
